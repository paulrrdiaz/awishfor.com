## Context

`MotifShape` (`src/components/shared/motif/motif-shape.tsx`) renders one of 16 shapes as `div.mot.m-<shape>` containing `SHAPE_CHILD_COUNT[shape]` absolutely-positioned `<i>` children, each painted by an `i:nth-child(n)` rule in `src/styles/globals.css` reading `background: var(--m1|--m2|--m3)`. The wrapper's `.m-<shape>` class also sets the shape's native pixel box (`width`/`height`), and a shared `.mot` rule applies `transform: rotate(var(--motif-rotate)) scale(var(--motif-scale)) translate(tilt)`. Five placement components (`MotifScatter`, `MotifSeal`, `MotifSticker`, `MotifBand`, `MotifDivider`) call `MotifShape` with per-instance `scale`/`rotate`/`opacity`/`tiltDepth`/`colors`/`surface`, ranging from `scale: 1.5` (hero scatter) down to `scale: 0.18` (band strip).

Two mechanisms this change must not disturb because five components and the catalog already depend on their exact shape:
- **Surface inversion**: `[data-motif-surface="primary"]` overrides `--m1`/`--m2`/`--m3`/`--mc1` in that DOM scope (band-treatment countdown chip and gift sticker). This is a CSS custom-property override, not a component-level branch — it works on any descendant that reads those variables, SVG included, with zero code change.
- **Secondary fixed colors**: `MotifShape`'s `colors` prop writes inline `--m1`/`--m2`/`--m3` overrides on the wrapper `div` when `surface === "base"` (fox, boat, balloon, leaf carry their own identity hue independent of the ambient palette). Same reasoning — inline custom-property overrides, orthogonal to how the color is consumed downstream.

Both mechanisms are custom-property overrides at the DOM level, not CSS selectors keyed to `.mot i:nth-child(...)`. This is what makes an SVG swap a pure rendering change: nothing about how colors *reach* a shape changes, only how a shape *consumes* them (`fill="var(--m1)"` on a `<path>` instead of `background: var(--m1)` on an `<i>`).

The design reference for the target illustration style is `add-motif-gallery`'s reviewed baby-animal references (bunny, duck, unicorn, dino, moon+stars) — soft rounded bodies, oversized eyes, blush cheeks, flat shading, no fine linework.

## Goals / Non-Goals

**Goals:**
- Every one of the 16 shapes becomes an inline `<svg>` illustration, recolored exclusively through `fill="var(--m1)"` / `var(--m2)` / `var(--m3)` / `var(--mc1)`.
- Zero changes to the `MotifShape` prop contract, and zero changes to any of the 5 placement components' call sites — this is an internal rendering swap.
- Zero changes to the surface-inversion and secondary-color-override mechanisms described above.
- Preserve each shape's native pixel footprint (the current `.m-<shape>` width/height) so every existing `scale` value across all 5 placement components continues to produce the same rendered size with no retuning.
- Legible from the smallest real usage (`mband` secondary shapes, ~8–10px rendered — see Risks) up through the largest (`120px`-class hero scatter primary).
- Drop the orphaned `horn` shape and its CSS.

**Non-Goals:**
- Any change to the motif catalog's data shape (`MotifPreset`, `secondaryColors`, `m3Inverted`, `suggestedThemeId`) — untouched.
- Any change to placement logic, scale/opacity/rotate *values*, or which motif appears where — untouched. If a specific illustration reads poorly at its assigned scale, that is a follow-up tuning task, not scope here.
- New theme presets, new motif sets, or additional hero-layout integrations — all out of scope, as in `add-motif-gallery`.

~~Animation, gradients, or filter effects inside the SVGs — flat fills only, matching the current flat-color system.~~ **Superseded — see Decision 3.** The first-pass flat-fill illustrations read as flat colored blobs next to the baby-shower reference art (chibi proportions, ink outlines, soft shading) the product actually wants. Gradients/shading are back in scope, animation is not.

## Decisions

### 1. SVG replaces the `<i>`-child model; a shape registry replaces `SHAPE_CHILD_COUNT`

`motif-shape.tsx` currently derives child count from `SHAPE_CHILD_COUNT` and renders that many empty `<i>` elements, letting CSS `nth-child` selectors do 100% of the visual work. The SVG version inverts this: a new module, `motif-shape-svgs.tsx`, exports `SHAPE_SVGS: Record<MotifShapeId, ShapeSvg>` where each entry supplies the shape's `viewBox`, native pixel `width`/`height` (ported unchanged from the current `.m-<shape>` CSS), and its JSX body (`<path>`/`<circle>`/`<ellipse>` elements with `fill="var(--m1)"` etc.). `MotifShape` becomes a thin wrapper: it resolves the CSS-variable overrides (`colors`, surface) exactly as today, then renders `<svg aria-hidden="true" viewBox={..} width={..} height={..}>{SHAPE_SVGS[shape].children}</svg>` inside the same `div.mot` transform wrapper.

Splitting the registry into its own module keeps `motif-shape.tsx` (the behavioral contract: scale/rotate/tilt/surface/colors) small and reviewable, separate from 16 illustrations' worth of path data.

**Rejected:** one JSX `switch` inline in `motif-shape.tsx` (mixes behavior and illustration data in one large file); one component-per-shape file (16 files for what is fundamentally lookup data, no shape has behavior of its own); a data-only format (JSON path strings) consumed by a generic renderer (adds an indirection layer for no reuse benefit — nothing else needs to consume raw path data, and JSX is more legible to edit than escaped path/JSON hybrids for anyone tuning a curve later).

### 2. Native shape dimensions move from CSS into the SVG's own `width`/`height`/`viewBox`

Today `.m-bear { width: 44px; height: 44px }` etc. lives in `globals.css`, one rule per shape, purely to size the box that `transform: scale()` then multiplies. Since each shape's SVG already needs a `viewBox` to author paths against, the natural sizing lives on the `<svg>` element itself (`width="44" height="44" viewBox="0 0 44 44"`), and the sixteen `.m-<shape> { width; height }` CSS rules are deleted along with the `i:nth-child` rules — nothing keys off `.m-<shape>` classes anymore. `.mot` (transform, position) and `[data-motif-surface="primary"]` (color override) are the only motif-shape CSS rules that survive; placement chrome (`.mdiv`, `.mband`, `.seal`, `.stk`) is untouched, since none of it is shape-specific.

Native pixel dimensions are ported 1:1 from the current CSS so every existing `scale` multiplier in `motif-scatter.tsx`, `motif-band.tsx`, `motif-sticker.tsx`, `motif-seal.tsx`, and `motif-divider.tsx` renders the same physical size as before. This is a hard constraint on `viewBox`/`width`/`height` selection, not a suggestion — retuning any placement's `scale` values is out of scope.

**Rejected:** keeping box sizing in CSS and having the SVG stretch to fill via `width: 100%; height: 100%` (adds a layer of indirection between "this shape is 44×44" and where that fact lives, for a value that will only ever be read by the SVG itself).

### 3. Illustration weight scales with viewBox complexity, not stroke width

**Amended mid-implementation.** The version below reflects the second pass, after the first flat-fill pass (ported directly from the old CSS box positions, no outline, no shading) was reviewed against baby-shower reference art and rejected as too crude — see "Rejected" for what changed and why.

At `~8px` (mband secondary instances) through `~120px` (hero scatter primary at high scale), the same path data must stay legible. Every shape is still authored as filled regions (paths/circles/ellipses) — no open, unfilled strokes for structural geometry, since thin strokes disappear or alias at 8px. Facial features (eyes, blush, nose) are sized proportionally to the shape's own viewBox (an eye is never less than ~8% of the shape's viewBox width), not fixed-pixel details that vanish when the whole shape shrinks below the detail's own size.

On top of that flat-region base, illustrations now carry:
- **Ink outlines** on major silhouette edges: `stroke="var(--m3)"` (or the shape's designated ink token) at a `strokeWidth` proportional to the viewBox (not a fixed px value, for the same downscaling reason as above). This is what the reference art's linework reads as up close; at ~8px it reads as a slightly crisper silhouette edge, which is still an improvement over no edge definition.
- **Shading and highlight**, via `fill="color-mix(in srgb, var(--m1) 80%, black 20%)"` (shadow) / `color-mix(in srgb, var(--m1) 70%, white 30%)` (highlight) — mixed from the region's own body token, never a bare hardcoded color. This is what makes shading theme-safe: swapping `--m1` (fixed → themed palette, or `surface="primary"`'s forced white) automatically recomputes the shading/highlight tone with it. Verified in-browser (Chrome) that `color-mix()` against `--m1: #ffffff` (the `primary` surface value) still produces a visibly distinct gray, not an invisible white-on-white — this was the specific failure mode considered and ruled out.
- **Gradients — considered, not used.** `<linearGradient>`/`<radialGradient>` need a `<stop>` element referenced by `id`, and `SHAPE_SVGS` entries are static JSX with no per-render identity: any shape rendered more than once on the same page (near-guaranteed — `MotifScatter` alone renders a shape several times, before counting `MotifSeal`/`MotifSticker`/`MotifBand`/`MotifDivider` on the same wishlist) would emit duplicate `id`s into one DOM, which is invalid and lets browsers resolve every instance's gradient to whichever `<defs>` happens to win. Scoping IDs per-instance (e.g. `useId()` threaded through the registry) is a real option but adds a second axis of change to registry's shape (`children: ReactNode` → `children: (idPrefix: string) => ReactNode`) for a visual effect `color-mix()`-based shading already delivers adequately. Deferred; not used in this pass. The `style="stop-color:var(--m1)"` vs. bare-attribute verification above is kept as a record of what was checked, in case a future shape's shading genuinely needs a spatial gradient badly enough to justify the id-scoping work.

**Kawaii group:** `bear`, `bunny`, `fox`, `unicorn`, `duck`, `dino`, `elephant` — full character treatment (oversized eyes, blush, rounded body silhouette, outline + shading per above). The goal statement's "non-animal shapes stay simple" list (`cloud, rainbow, star, moon, balloon, tree, leaf, boat`) is eight items and does not include `elephant`; the earlier "animal shapes already got a first-pass cuteness pass" list (`bear, bunny, fox, unicorn, duck`) scopes what's *already shipped*, not the full target set — `dino` is absent from both lists and is unambiguously kawaii by the reference images, and the same reasoning puts `elephant` in this group: two of the session's reference images are faced baby elephants, and `elephant` is `elephant-balloon`'s *primary* shape, rendered in the seal/sticker/countdown-chip placements alongside faced bears, bunnies, foxes, and ducks in every other set. A faceless elephant in those same placements would be the exact inconsistency this change exists to remove.

**Geometric group:** `cloud`, `rainbow`, `star`, `balloon`, `tree`, `leaf`, `boat`, `flower` — simplified curves with the same outline/shading treatment, no character features (no eyes/blush). `moon` is a second exception alongside `elephant`: the pasted "Sweet Dreams" reference is a sleepy-faced moon, pasted specifically against this shape, so `moon` gets a small closed-eye/blush face despite sitting in the otherwise-faceless prop group — narrower than reclassifying it into "kawaii" outright, since it's a sleepy/closed expression, not the kawaii group's oversized-open-eye treatment.

**Blush color token:** the current CSS already establishes the mechanism — `background: var(--m3); opacity: 0.2–0.22` (see `.m-bunny i:nth-child(7-8)`, `.m-unicorn i:nth-child(10)`). Port this as-is: blush ellipses use `fill="var(--m3)" fill-opacity="0.2"` (or the shape's existing authored value), no new token. This composes correctly under `data-motif-surface="primary"`: `--m3` resolves to `m3Inverted` there, so blush renders as a faint dark tint at the same opacity rather than pink — an existing, already-shipped behavior this change carries forward unchanged, not a new design question.

**Reference coverage:** the reference images collected mid-review cover `dino`, `bunny`, `duck`, `moon`, `elephant`, `unicorn` — 6 of 16 shapes. Those 6 are re-authored first and shown for approval before extrapolating the outline/shading/gradient technique to the remaining 10 (`bear`, `fox`, `cloud`, `flower`, `rainbow`, `tree`, `boat`, `balloon`, `star`, `leaf`), to avoid re-doing all 16 against a guessed style a second time.

**Rejected:** a uniform "one style for all 16" (contradicts the goal statement's explicit animal/non-animal split); a new `--blush` token (unnecessary — `m3` + opacity already does this in production); flat fills with no outline/shading (the first pass — rejected by product review as reading like colored blobs, not the intended kawaii illustration style); bare `stop-color="var(--m1)"` presentation attributes for gradient stops (unverifiable Safari support — see above).

### 4. Staged rollout rejected — ship all 16 shapes in one change

Considered shipping shapes incrementally (e.g., animals first, then geometric shapes; or motif-set by motif-set) behind a per-shape flag inside `MotifShape`. Rejected:
- Every motif set pairs one animal-or-character shape with one prop shape (`bear-cloud`, `flower-bunny`, `unicorn-rainbow`, `forest-fox`, `duck-boat`, `elephant-balloon`, `moon-stars`, `dino-leaf`). Shipping one half of a pair as SVG and the other as CSS boxes would render a single motif set in two visibly mismatched styles — worse than the current fully-consistent (if boxy) look, for every user who has any motif selected in the interim.
- There is no external risk this staging would reduce: no schema change, no new dependency, no user-facing config toggle to gate. The entire surface is reviewable in Storybook (`motif-shape.stories.tsx` already renders all 16 at multiple scales) before merge, which is where illustration quality should be caught — not in production behind a flag.
- A flag mechanism (e.g., `SHAPE_SVGS` falling back to a legacy CSS renderer per shape) is itself the kind of scaffolding this codebase's conventions avoid for a one-time migration with no rollback need beyond `git revert`.

Ship as one PR touching all 16 shapes, the catalog (`horn` removal), and the CSS deletion together.

### 5. Update the unarchived `add-motif-gallery` docs directly, plus this change's own spec delta

`add-motif-gallery` shipped in code (all tasks checked) but was never run through `opsx:archive`, so `openspec/specs/public-wishlist-motifs/spec.md` does not exist yet at the top level — only `openspec/changes/add-motif-gallery/specs/public-wishlist-motifs/spec.md` and `openspec/changes/add-motif-gallery/design.md` exist, both still living in an active (unarchived) change directory.

Two edits happen during apply, both in scope for this change:
1. This change's own `specs/public-wishlist-motifs/spec.md` delta (below) states the new requirement in standard OpenSpec `MODIFIED Requirement` form, referencing `add-motif-gallery`'s spec as the effective baseline (see proposal.md note).
2. `add-motif-gallery/design.md` Decision 1 ("Pure-CSS shape primitives, not SVG") and `add-motif-gallery/specs/public-wishlist-motifs/spec.md`'s "Motif shapes render as CSS primitives" requirement are edited in place to reflect the SVG decision, since that change is still a draft (unarchived) rather than historical record — leaving it internally contradictory (an unarchived change whose own docs argue against what the codebase now does) would be a worse outcome than correcting it. This is not "rewriting history": nothing about `add-motif-gallery` has been archived yet, so its documents still describe current intent, not a closed decision. Critically, the requirement **header text itself** — not just its body — gets renamed to "Motif shapes render as inline SVG" (matching this change's own delta header exactly). `add-motif-gallery` has not archived yet, so if it archives *before* this change does, it will write `openspec/specs/public-wishlist-motifs/spec.md` fresh from its own (edited) text; this change's `MODIFIED Requirements` header must match that eventual top-level header verbatim, or the archive tooling will fail to locate the requirement it's meant to replace.

**Rejected:** leaving `add-motif-gallery`'s docs untouched and letting this change's delta silently supersede them (the two documents would then actively contradict each other with no pointer between them, for a change that isn't even archived — confusing to anyone reading `add-motif-gallery` next); archiving `add-motif-gallery` first as a prerequisite (out of scope for this proposal, and not necessary — editing an unarchived change's own docs is safe and reversible).

## Risks / Trade-offs

**No placement actually clears the stated 16px legibility floor at current native sizes and scales** — `mband` secondary instances (scale 0.18–0.24 on ~44–54px native shapes ≈ 8–13px) and `MotifSticker` (`scale: 0.32` on primary-shape native sizes 26–50px ≈ 8–16px, e.g. `moon` at 26px → 8.3px, `unicorn`/`elephant`/`dino` at their largest → ~15px) both land below or at the boundary of 16px. Verified separately: the "countdown chip" placement described in `add-motif-gallery/design.md`'s placement table and marked complete in that change's task 5.6 is not actually wired — `countdown.tsx` and its call site in `public-wishlist-body.tsx` pass no motif props today, so it renders no motif icon to check against. This gap predates and is unrelated to this change's scope (a rendering-mechanism swap, not new placement wiring) and is called out here only so the 16px figure isn't asserted against a placement that doesn't exist yet. Accepted: author to an effective floor of ~8px (the smallest real, verified usage — `mband`, and `moon` at sticker scale), treating anything below ~14px as texture rather than a recognition moment; retuning `scale` values in `motif-band.tsx`/`motif-sticker.tsx`, or wiring the countdown icon, are follow-ups outside this change.

**Illustration quality is subjective and reviewed via Storybook, not an automated check** → `motif-shape.stories.tsx` must render all 16 shapes (and both surfaces) so quality review happens before merge; tests assert only structural properties (an `<svg>` is present, `<title>`/`<desc>` are absent, `aria-hidden` is set, fills reference the three custom properties) — visual correctness (does the bear look like the reference) is a human judgment call at review time, same as it was for the CSS shapes' "first-pass cuteness" work already merged.

**Editing `add-motif-gallery`'s own docs mid-flight** → Bounded to the two places called out in Decision 5 (one design decision, one spec requirement); the rest of that change's docs (catalog shape, placement split, persistence, tilt) are unaffected and stay as-is.

**No visual regression safety net** → This repo has no screenshot-diff tooling. Manual verification (dev server, real published wishlist, multiple motif sets/treatments/surfaces) is the acceptance gate, same as `add-motif-gallery`'s own validation task did.
